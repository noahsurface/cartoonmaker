# Build notes

Running log of what was built and any non-obvious decisions, as the app is built out in one long pass.

## Architecture

- Plain ES modules, no build step, no framework, no backend. `index.html` loads `src/main.js` as a module; a tiny hash router (`#/home`, `#/assets`, `#/characters`, `#/scenes`, `#/editor?id=`, `#/puppet?id=`, `#/export?id=`) swaps view modules in and out of a single `<main>` element.
- Persistence is IndexedDB via `src/db.js` (generic get/getAll/put/delete over `assets`, `characters`, `objects`, `scenes` stores). Uploaded images are stored as `Blob`s; `getAssetUrl()` lazily creates and caches `URL.createObjectURL()` values.
- `src/seed.js` imports the bundled sample art from `assets/samples/` into the asset store under fixed ids the first time the app runs (idempotent — safe to call on every boot), plus starter characters, objects, and a starter scene, so the app is usable with zero uploads. Bundled characters are declared as a small array of specs (id, display name, asset-id prefix, local art folder) fed through one generic seeding routine, rather than duplicated per-character code — currently "Bruce" (placed in the starter scene) and "Reggie" (seeded and available in the library, not placed by default). Bundled objects (currently just "Bush") follow the same array-of-specs pattern, seeded and available in the library/editor but not placed by default.

## Asset library folders

Assets can be organized into flat (non-nested) folders — a new `folders` IndexedDB store (`{id, name, createdAt}`), with each asset gaining an optional `folderId` (unset = unfiled). A fixed, non-deletable **System** folder (id `'system'`) is seeded alongside the other bundled content and holds the shared shadow and speech-bubble frames specifically, per spec; every other bundled asset (backgrounds, character art, Bush) is left unfiled by default, since organizing those is the user's own call, not something to pre-decide for them. Deleting a folder un-files its contents rather than deleting them — a folder is purely an organizational label, never a container the assets' existence depends on.

The picker modal used to choose an image (`views/asset-picker.js`) — shared by the Characters builder, the scene editor's background picker, and object creation — is folder-aware the same way the Assets library page is: a row of folder chips filters the grid, and uploading a new image while browsing a folder lands it there directly. This is the same modal in every context, so a folder made to organize backgrounds is just as easy to navigate into whether you're picking a scene's background or an object's art.

Existing installs (already-seeded shadow/bubble assets predating folders) are patched into the System folder by a one-time `migrateFxAssetsIntoSystemFolder()` fixup, run alongside the app's other startup migrations — `seedSampleContent()`'s own folder assignment only applies at asset-creation time, so it can't retroactively fix already-existing records.

## Character model

A character has three parts: any number of named **poses** (each an independently-posed `body` layer — see "Multi-pose characters" below), plus one shared `mouth` layer and one shared `eyes` layer, each a list of labelled frames (`{id, label, assetId}`) plus a `roles` map that says which frame(s) are special:

- Each pose's body layer: `roles.idle` (single frame), `roles.cycle` (ordered list, played on a loop while the character is moving — there's no true walk-cycle art, so this cycles through whatever frames the user assigns).
- `mouth.roles.silent` (single frame), `mouth.roles.talk` (ordered list, looped while the talk button/key is held).
- `eyes.roles.forward` / `side` / `blink` (single frames each).

The active pose's body, plus mouth and eyes, are drawn on top of each other at the same anchor point every frame. This only works because the sample art is authored that way (all layers are 1200x1200 canvases pre-aligned to a shared origin) — the character builder doesn't do any per-frame offset editing, it assumes new custom characters follow the same convention (documented in the Characters view's help text). The library's character thumbnail composites body (idle) + mouth (silent) + eyes (forward) the same way — via three stacked, absolutely-positioned `<img>` elements rather than an offscreen canvas, since all three share the same canvas size and are already pre-aligned — so it shows the character's fully assembled resting look instead of just a bare body with no face.

## Multi-pose characters

A character can have several named poses (e.g. idle, hands-up, running) instead of just one body — each pose is its own body layer with the same idle/cycle-frame shape a single body used to have, so a pose can be as simple as one static frame or as rich as its own multi-frame movement cycle. Mouth and eyes stay shared across every pose (unaffected by which one is active), and sway/bounce keep applying regardless of pose, by design — a pose changes what's drawn, not how the existing motion machinery moves it.

`getCharacterPoses(character)` (`engine/character.js`) is the one place that reads a character's poses, normalizing older characters (saved with a single `layers.body`, before this existed) into an equivalent single-pose shape on the fly — a read-only fallback, not a migration. The actual one-time persisted migration (`layers.body` → `poses: {id: {...}}, poseOrder: [id]`) happens in the character builder (`views/characters.js`) the first time such a character is opened there, the same self-healing pattern used for `baseScale` earlier.

Per scene, per placed character entity, `entity.poseSequence` is an ordered (and possibly repeating — e.g. `[idle, handsUp, idle, running, idle]`) list of pose ids. While recording, the left/right bumper (or `[`/`]`) steps an index through that list, wrapping at both ends; the scene editor builds this list with an append-from-palette + remove-by-chip UI rather than free reordering, since an ordered, repeatable loop is the actual use case and needs much less UI than a general reorder control. The current pose index is sampled into the recorded track exactly like `mouthHeld` is (see "Recording model"), so played-back and exported animation reproduces pose changes at the right moments — not just live puppeteering.

Switching pose plays the same paper-flip transition as a direction reversal, but must land back on the *same* facing rather than the opposite one — a pose swap shouldn't also mirror the character. `CharacterAnimState` tracks this with its own `poseFlipT`/`_priorPoseId` pair (separate from the direction-flip's `flipT`/`flipFrom`), using `poseFlipScale = |cos(poseFlipT · π)|` — the same curve shape as the direction flip, just made non-negative so it shrinks to edge-on and grows back out on the same side instead of crossing into a mirrored, opposite-facing state. The displayed pose (`state.displayPoseId`) lags the logical one (`state.activePoseId`, which updates immediately, exactly like `facing` does for a direction change) until the transition passes its edge-on midpoint, so the art swap is hidden behind the flip rather than popping while still fully visible. Stepping to a pose that's already active (e.g. idle → idle in a sequence like `[idle, idle, running]`) is a no-op — no flip plays — since the flip is only armed when the *desired* pose id actually differs from the current one. Verified analytically (calling `CharacterAnimState.update()` directly with controlled `dt` steps) rather than by eyeballing an animation-frame-timed screenshot: `displayPoseId` lags correctly, the combined `scaleX * poseFlipScale` never goes negative through a pure pose-change flip, and an identical next pose leaves `poseFlipT` at 1 (settled) the whole time.

Shadow width-matching (see below) is measured per **(character, pose)** pair, not once per character, since different poses can have meaningfully different silhouette widths.

## Coordinate system

Entity positions are stored as absolute pixels in a fixed 2560x1440 reference space (`src/engine/coords.js`), matching the sample background's native resolution — not normalized 0..1. This matters because it's what makes movement speed/acceleration isotropic (the same in x and y); a 0..1-per-axis scheme would silently move faster vertically than horizontally, since the background isn't square. Every windowed render target (the 1280x720 live stage, a 1920x1080 export) is a uniform scale of this same REF_WIDTH x REF_HEIGHT space (`scale = canvas.width / REF_WIDTH`) — that's the definition of the camera's fixed zoom level — so nothing needs to change per resolution.

A scene's **world** can be bigger than that on either axis, or both at once: the background is drawn at its own true native pixel dimensions rather than being stretched to fill the frame, floored at the standard REF_WIDTH x REF_HEIGHT size on each axis independently (`computeWorldSize()`) — one image pixel is one reference-space pixel. A background at least as big as standard on an axis is drawn there with zero distortion, and the excess becomes that axis's scrollable range; an axis smaller than standard is stretched up to fill the frame (matching this app's original behavior, before scrolling existed, of always stretching a background to fill the frame exactly). A background at exactly REF_WIDTH x REF_HEIGHT — every background before this existed, and the bundled sample — yields that back exactly, so existing scenes are pixel-for-pixel unaffected.

This native-pixel-dimensions approach replaced an earlier "CSS `background-size: cover`"-style formula (one scale factor picked so both dimensions are at least standard-sized) during this same round, once testing caught that a cover-style scale can *only ever* leave one axis with excess by construction — it's mathematically impossible for both worldWidth and worldHeight to exceed standard at once under that formula, which would have made genuine diagonal scrolling impossible no matter what background was uploaded. Using each axis's own pixel size independently doesn't have that problem: an image bigger than standard in both dimensions (e.g. a big single-image map) yields a world bigger in both, and a diagonal camera pan is just both axes panning at their own independent rate.

## Camera

Camera follow (`engine/camera.js`, `CameraState`) on whichever axes the world is actually scrollable on, designed the same way as `CharacterAnimState`: it's a pure function of a position stream (the designated "focus" character's x/y each frame, from `scene.cameraFollowEntityId`) plus `dt`, so it re-derives identically for live puppeteering, played-back tracks, and export with **no separate camera recording** — `SceneRuntime` just calls `camera.update()` during its normal render pass, using whichever entity's resolved position that frame already provides. The two axes are independent deadzone-follows (see below) computed with the same per-axis helper, so a diagonal pan is nothing more than both axes moving at once — there's no special-cased diagonal logic.

The follow behavior is a classic deadzone camera: the focus character can move freely within a zone near the center of the frame; only once they'd go outside it does the camera start panning, easing (not snapping) toward keeping them at the deadzone's edge, clamped so it never shows past the world's actual edges. A `dt <= 0` call (a static preview draw, or a manual timeline scrub) snaps straight to centering the focus character instead of easing — this matters because otherwise scrubbing the timeline while paused would show a stale, previously-eased-to position rather than the framing that time actually calls for; verified by scrubbing straight back to t=0 after a long pan and confirming the exact original framing returns, byte-for-byte.

One scene-level setting: `scene.cameraFollowEntityId` (a character entity id, or unset for a static camera — the old, only, behavior). No follow target, or a background at standard aspect on both axes (so there's nothing to scroll to regardless), and the camera is a no-op; this is why nothing needed to change for any existing scene.

`SceneRuntime.render()` takes an `opts.fullWorld` flag: false (the default, used by Animate and Export) shows the normal windowed camera view; true (used only by the scene editor) shows the **entire** world zoomed out to fit the canvas instead, ignoring camera follow entirely, letterboxing whichever axis has slack once the other is fully used — so everything in a large scene can be placed at a glance without any pan/scroll UI of its own. `getWorldTransform()` computes the scale/letterbox-offsets for both modes from the same inputs, and the editor's own drag-and-drop hit-testing uses that identical transform (rather than a separate hardcoded one) so what you can click matches what's drawn.

## Movement & animation feel (paper-cutout aesthetic)

This was the part most worth getting right, so it's centralized in `src/engine/character.js`:

- **Physics**: `TrackRecorder` (`src/engine/recorder.js`) integrates a velocity that accelerates/decelerates toward the input direction at a fixed rate (2000 px/s²) up to a max speed (500 px/s), rather than snapping to a target velocity — matching a specific request for that exact feel. Diagonal input is normalized so it isn't faster than a single axis.
- `CharacterAnimState` is a tiny state machine that is fed nothing but a stream of absolute (x, y) positions + dt (+ whether the character is currently talking). It derives everything else: whether the character is "moving" (speed above a threshold), a walk phase used for sway/bounce, a facing flag, automatic eye direction, and independent random blinking.
- **Sway**: a rotation (not a translate) of ±7°, pivoted at the character's feet — `ctx.rotate()` around the same point the body/mouth/eyes are anchored to, so the head swings side to side while the feet stay planted. One full sway cycle takes a fixed 0.75s while moving (not scaled by speed). **Bounce** lifts the same pivot straight up (never down, so feet never dip below the shadow), height = 6.7% of the character's rendered height. Both are driven by the same `walkPhase` — sway is `sin(walkPhase)`, bounce is `abs(sin(walkPhase))`, which has exactly half the period, so bounce completes two full up-down cycles (0.375s each) per one sway cycle for free, with no separate rate to keep in sync. When the character stops, `walkPhase` eases toward the *nearest multiple of 2π* rather than freezing mid-step, so sway/bounce decay to zero smoothly instead of snapping.
- **Paper-flip turn**: when horizontal direction reverses, we start a 0.32s transition and compute `scaleX(t) = flipFrom * cos(t * π)`. At t=0 this equals the old facing (±1); at t=1 it equals the new facing (∓1); at t=0.5 it passes through exactly 0 — the character goes edge-on, like a card flipping.
- **Automatic eyes**: no button controls these at all. Eyes show the side-look frame whenever horizontal speed exceeds a small threshold, forward otherwise (vertical-only movement, or standing still). Because the eyes layer is drawn inside the same rotated/flipped transform as the body, a character moving left automatically mirrors the same "side" art that a character moving right uses — no separate mirrored asset needed.
- **Blinking**: each `CharacterAnimState` keeps its own independent timer, randomized 2-4s, that triggers a 0.125s blink (overriding whatever eye frame was showing, then reverting to it) — this runs for every character in a scene continuously, including ones that are just sitting at their placed position with no recorded track.
- **Shadow**: the uploaded shadow art (not a drawn ellipse), positioned every frame at the character's raw (x, y), *before* the sway/bounce/flip transform, so it tracks movement but doesn't wobble, tilt, or flip with the body above it. Its width is scaled to match the character's actual (non-transparent) silhouette width, not the full padded art canvas — measured once per character by scanning its idle body frame's alpha channel (`getContentWidthFraction` in `utils/image-cache.js`, cached per image) rather than a single guessed constant, so it's correct for any character's proportions, not just one specific art style.
- **Speech bubble**: while a character is talking (mouth held), a 4-frame bubble loops at 8fps, centered above and to the right of the bottom of the character's feet. The offset is expressed as a *fraction* of the character's rendered size (`BUBBLE_OFFSET_X_FRACTION`/`BUBBLE_OFFSET_Y_FRACTION` in `engine/character.js`, derived from the original 400px/200px-at-default-scale spec) rather than a fixed reference-space pixel amount, so scaling a character up or down in the scene editor moves and resizes the bubble proportionally instead of leaving it pinned at the old absolute position. It translates and bounces with the character but does not inherit the sway rotation or the facing flip — it stays upright. Bubbles are drawn in their own pass after every character's body (see "Depth sorting" below), so they always sit on top of everyone, and each one's opacity drops to 50% while its rectangle overlaps another character's bounding box (`rectsOverlap` in `engine/character.js`), returning to full opacity once it doesn't, so the covered character stays readable underneath.

## Scene editor scale UX

Each placed entity stores both `scale` (the actual render scale, `size = scale * canvasHeight`) and `baseScale` (the scale it was placed at, treated as its "1x"). The scale slider shown in the editor is a multiplier (`scale / baseScale`), snapped to 0.5x steps from 0.5x to 4x, with the current value shown as a label ("1x", "1.5x", etc.) instead of a raw number — moving the slider sets `entity.scale = entity.baseScale * multiplier`. Entities saved before `baseScale` existed fall back to treating their current `scale` as 1x the first time they're selected (`entity.baseScale = entity.baseScale || entity.scale`), so old scenes don't jump in size.

## Object shadows

Objects/props have an optional shadow toggle (`entity.hasShadow`, off by default), drawn with the same shadow art and the same non-transparent-width-matching approach as character shadows (`getContentMetrics().widthFraction`, measured per object too and cached in `SceneRuntime.shadowWidthFractionByObjectId`). Unlike characters, whose shadows are always on, this is opt-in per placed object since not every prop should visually read as "standing" on the ground (e.g. something meant to lie flat or hang).

The shadow's vertical anchor is also detected from the art rather than assumed. A character's shadow is centered on the character's placement point directly, which is correct because `FEET_ANCHOR_Y` is a hand-authored convention that already accounts for padding below the feet in every character's art. Objects have no equivalent convention, so an object image with any transparent padding below its visible silhouette (as the bundled Bush's does — it isn't cropped tight to the foliage) left its shadow floating visibly below the real base once shadows were checked against actual art rather than just the math. The fix: `getContentMetrics()` (`utils/image-cache.js`) now also returns `bottomFraction` (how far down the lowest non-transparent pixel sits, as a fraction of the full image height — 1 means no padding) in the same alpha-channel scan already done for width-matching, and the shadow is centered at that detected base (`oy - dh * (1 - bottomFraction)`) instead of at the image's raw bottom edge. Verified by comparing a before/after screenshot of the bundled Bush at 3x scale — the visible gap between the foliage and its shadow closed completely.

## Solid objects

Objects/props have a second optional toggle, `entity.solid`, that blocks characters from walking into them — a simple, cheap AABB-vs-point collision, since a character's position is already treated as a single point everywhere else in this app (e.g. the world-edge clamp). The collision zone is shaped like the object's *shadow* (same width-matching, same detected-base anchor from the fix above) rather than its full rendered height, deliberately: a full-bounding-box block would fight the existing Y-based depth sort, since a character with a lower Y than a tall solid object should still be able to walk in front of (or behind) it — only its ground footprint should actually be impassable. `SceneRuntime.getSolidObstacles()` computes each solid object's footprint rectangle once (objects don't move), and `TrackRecorder.step()` (`engine/recorder.js`) pushes a tentative position back out along whichever edge of an overlapping obstacle is nearest, zeroing velocity on whichever axis that push happened on — the same "stop, don't relaunch" treatment the world-edge clamp already used. Verified by placing a solid object precisely in a character's path (computing the exact placement needed to align with the *detected* footprint band, not the raw entity position, using the app's own metrics rather than guessing) and confirming the recorded track never crosses it, then confirming the same walk passes straight through once solid is toggled back off.

## Depth sorting

Characters and objects are drawn in Y order each frame — greater y (further down the scene) is drawn later, on top — recomputed every frame from each character's *current* live/track position (`SceneRuntime.render()` in `engine/scene.js`), not the static value set via the scene editor's "Send back"/"Bring front" buttons. Those buttons still work, but now only as a tiebreaker when two entities share the same y; the primary sort key is dynamic. This applies uniformly to characters and objects, so a character can walk in front of or behind a prop by moving to a different y, matching how it's expected to look in a real 2D scene. `drawCharacterBody()` intentionally excludes the speech bubble so this depth pass can finish (and every character's bounding box be known) before bubbles are drawn on top in a separate pass.
- **Talking**: mouth and body both cycle through their `talk`/`cycle` frames in lockstep at 10fps, driven by a `talkClock` that runs only while the talk button/key is held (reset to 0 each time a new utterance starts) — not by movement or by the same clock as anything else. An earlier version of this accidentally reused the movement-driven pose clock for the mouth, so it only advanced while the character was walking and looked frozen on frame 0 while talking-in-place; `talkClock` is now a separate, dedicated clock for exactly this.
- Because this state machine only depends on a position (+talking) stream, the exact same `update()`/`drawCharacter()` pair is used for live puppeteering, played-back recorded tracks, and video export — movement looks identical in all three.

## Recording model

Recording a character does *not* bake in sway/bounce/flip/eyes/blink/talk-cycle-frame-index — it only stores what the user actually controlled: a timestamped list of `{t, x, y, mouthHeld, poseId}` samples (`src/engine/recorder.js`). Everything else visual (including eye direction, blinking, and which frame within a pose's cycle is showing) is re-derived at playback time from that stream, same as during live control. Interpolation is linear for position; `mouthHeld` and `poseId` are step functions (hold the last sample's value) since both are discrete, edge-triggered inputs, not continuous ones.

`TrackRecorder` also clamps movement to the scene's actual `worldWidth`/`worldHeight` (passed in at construction, along with any solid-object obstacle rectangles — see "Solid objects"), not hardcoded REF_WIDTH/REF_HEIGHT, so a character can walk the full extent of a large, scrollable scene rather than being capped at one camera-frame's size.

Layered recording (record character 1, then record character 2 while character 1's track plays back, etc.) works by having the scene renderer accept one `resolvePose(entityId)` callback that returns either a live-input-driven position (for the character currently being recorded) or a `sampleTrackAt(track, t)` lookup (for every previously-recorded character) or `null` (falls back to the character's static placed position from the scene editor, for anyone not yet recorded).

Pressing Record doesn't start recording immediately — it enters a `'countdown'` puppet-view mode (distinct from `'idle'`/`'recording'`/`'previewing'`) that shows a 3-2-1 overlay on the stage for one second per number, giving the user time to get their hands back on the keyboard/gamepad, before actually constructing the `TrackRecorder` and starting the capture loop. The countdown is cancelable via the same Stop button (it's left enabled, unlike Record) — canceling just resets straight back to idle rather than recording anything, so no empty/junk track gets created. The countdown itself is never part of the recorded track's timeline (`t=0` in the saved track is the instant actual recording begins, after the countdown), so scene/track durations are unaffected.

## Punch-in re-recording

Before this, fixing any part of a character's (or sticker's) take meant re-recording the whole thing from scratch — there was no way to redo just a stretch of it. Punch-in lets you scrub the timeline (clicking it already moved the idle-preview playhead; nothing new there) to a point partway through an *already-recorded* entity's track, hit Record, and have the new take replace everything from that point onward while keeping everything before it exactly as it was.

This only engages when the armed entity already has a track — `punchInTime = scene.tracks[armedEntityId] ? sceneTime : 0`, captured once, right when Record is clicked (before the countdown, so later scrubbing or arming-another-entity, which can't happen while the controls are disabled, can't change it mid-flight). An entity with no track yet always records a fresh take starting at 0, regardless of where the timeline happens to be scrubbed — otherwise just having reviewed the scene by scrubbing around, then arming a brand-new character, would silently start its very first take mid-timeline, which nobody would expect. A small hint above the Record button (`Punching in at 1.2s — Record will replace this track from here on, keeping everything before it.`) makes the non-zero case visible before it's committed to, rather than being a silent behavior change.

**The countdown shows the actual punch-in point.** The 3-2-1 overlay doesn't touch the canvas at all (it's drawn in a separate absolutely-positioned element on top) and nothing else redraws the stage during the countdown's `sleep()` loop, so whatever was already on screen — the scrubbed-to frame, showing every entity exactly as they are at that instant — just stays there, overlaid by the countdown, for the entire 3 seconds. This happened to require no new code; it's simply what was already true once the old hardcoded "always reset to t=0" was removed from the recording-start path.

**Seeding for a jump-free start.** `TrackRecorder` gained a `startTimeOffset` constructor param (default 0): every sample it pushes is now stamped `startTimeOffset + elapsed`, i.e. an absolute scene-time `t`, rather than always restarting at 0. At punch-in, the recorder is also *seeded* from the old track's own interpolated sample at the punch-in instant — `sampleTrackAt(existingTrack, punchInTime)` — rather than the entity's static placed position: its `x`/`y` become the recorder's start position, a character's pose index is matched into the armed pose sequence (`poseSequence.indexOf(seedSample.poseId)`) so pose-stepping continues from the right spot instead of resetting to the sequence's first pose, and a sticker's visible/hidden state carries over the same way (not explicitly asked for, but the direct sticker analog of seeding a character's pose — otherwise a sticker that was visible right before the punch-in would instantly vanish the moment the new take started). The dialogue audio and every other entity's own track are likewise just left to play from `sceneTime = punchInTime` onward rather than being reset to 0, the same `sampleTrackAt(track, sceneTime)` call every other entity already used during any recording — punch-in didn't need to change that at all, just not reset the clock it reads.

**Splicing at Stop.** The new take's samples all carry absolute `t` values at or after `punchInTime`. The saved track becomes `[...oldTrack.samples.filter(s => s.t < punchInTime), ...newTake.samples]`, with duration taken from the merged array's last sample — i.e. literally "keep the old prefix, overwrite everything from here with the new take," including discarding anything the old track had *after* wherever the new take happens to stop (an explicit choice: a punch-in isn't bounded by the old track's original length, and there's no separate "punch-out" marker — Stop is the only out point).

Testing (described further in "Testing" below) verified the splice byte-for-byte: recorded a known original take, punched in partway through moving the opposite direction, and confirmed the resulting track's prefix is pixel-identical to the original up to the exact punch-in instant, the new segment starts within half a pixel of the original track's own interpolated position there (not a jump to the entity's placed position), and the final duration reflects the new take's own (shorter) length rather than any remnant of the original tail.

## Stickers

A sticker is a third entity kind alongside characters and objects: art that can be moved around like a character, but — unlike a character, which is visible from the start — starts a scene hidden and is puppeteered to appear/disappear at a chosen moment, same as its position is puppeteered. Rather than build a separate declarative "appear at t=2.3s at (x,y)" timeline, it reuses the existing live-performance pipeline wholesale: a sticker is armed and recorded exactly like a character (same `armed-select`/Record/Stop flow in Animate, same arrow-keys-or-stick movement, same `TrackRecorder`), just with Space/face-button-A/right-trigger repurposed from "hold to talk" into an edge-triggered appear/disappear toggle. This is a smaller change than it sounds, because that signal was already a plain boolean (`sample.mouthHeld`) with no other meaning baked into `input.js` — `puppet.js` just diffs it frame-to-frame itself (`if (sample.mouthHeld && !prevMouthHeld) stickerVisible = !stickerVisible`) only while the armed entity is a sticker, rather than passing it straight through as "currently held".

This meant generalizing two places that used to assume a character-shaped sample:
- `TrackRecorder.step()` took positional `(dx, dy, dt, mouthHeld, poseId)`; it now takes `(dx, dy, dt, extra)`, spreading whatever fields the caller passes (`{mouthHeld, poseId}` for a character, `{visible}` for a sticker) straight into the sample. `TrackRecorder` itself never inspects these — it only moves `x`/`y`.
- `sampleTrackAt()` used to explicitly destructure `mouthHeld`/`poseId` out of a sample; it now spreads every field from the bracketing sample generically (`{...first}`, `{...a, x, y}` for the interpolated case), so a sticker's `visible` field comes back out the same way a character's `mouthHeld`/`poseId` already did, with no per-kind branching needed in the sampler. The one exception kept explicit: `mouthHeld` is still forced `false` once `t` runs past the track's end, so a character doesn't appear to talk forever after its last recorded sample — `visible` has no equivalent forced-off, since the whole point is that a sticker *should* stay in whatever appear/disappear state it was last toggled to.

`SceneRuntime` picks sticker art up from a new `stickers` IndexedDB store and `stickerById` map (threaded through every `SceneRuntime` constructor call — editor, puppet, export — the same way `objectById` already was), and treats a sticker like an object for drawing purposes (no shadow, not solid, participates in the ordinary Y-depth sort) except for how its "hidden" state actually renders, which differs by context: `fullWorld` (the scene editor) always shows it at full opacity, since it has to be visible there to be placed/dragged in the first place; the Animate stage (`ghostHidden`, see below) shows it faintly even while hidden; everywhere else — export's final render — a hidden sticker is skipped and drawn nowhere at all, matching "a sticker does not start the scene as visible" in the actual output.

A sticker also isn't confined to the walkable ground band characters are kept in. `clampToBounds()` (`engine/coords.js`) and `TrackRecorder` both gained a `groundedY` parameter (default `true`, unchanged for characters) — `false` allows the full vertical extent of the world (minus the same small edge margin used for x), since a sticker is conceived as a floating overlay (a thought bubble, an exclamation mark popping in near the top of frame) rather than something standing on the ground. `puppet.js` passes `groundedY=false` (and an empty obstacles array — stickers aren't blocked by solid objects) only when constructing the `TrackRecorder` for a sticker recording.

The stickers library section in the Characters & Objects view reuses the exact same "name + single image, no layers" editor the Objects section already had — that editor was genericized from `renderObjectEditor()` into `renderSimpleItemEditor()`, parameterized by which store (`'objects'` or `'stickers'`) it's operating on, rather than duplicating the same rename/change-image CRUD a third time.

**Ghost opacity in Animate.** A completely invisible hidden sticker made it hard to tell where you were actually moving it before deciding when to toggle it on, so the Animate view specifically (not the editor, not export) draws a hidden sticker at 10% opacity instead of skipping it, and at 100% once toggled visible. This is a third `render()` option, `opts.ghostHidden`, passed by every `puppet.js` call site (static draws, the live recording loop, and preview playback) but by nobody else — `export.js` is intentionally left alone so the final output still shows nothing until a sticker is actually toggled on, and the editor is intentionally left alone since it already shows stickers at full opacity unconditionally for placement. Implemented as a plain `ctx.globalAlpha` around the sticker's draw call; verified precisely (not just eyeballed) by rendering the same sticker both visible and hidden and confirming the hidden pixel's color is exactly a 10%-toward-sticker blend of the background color, channel by channel.

**Movement.** Each sticker entity has a `movement` field — `'static'` (default), `'bounce'`, `'sway'`, or `'spin'` — set via a dropdown in the scene editor's entity-controls panel (sticker-only, the same slot objects use for their shadow/solid checkboxes and characters use for their pose-sequence editor). This drives a small continuous animation, active only while the sticker is actually toggled visible, computed in `SceneRuntime.render()` from a new per-sticker `StickerAnimState`: a single `visibleClock` that resets to 0 the instant the sticker transitions from hidden to visible (so motion always starts from neutral at the moment of appearing, never mid-cycle) and snaps straight back to 0 while hidden (so toggling off instantly returns the sticker to its undisplaced, unrotated neutral pose, per spec, rather than freezing wherever the animation happened to be). Bounce offsets the sticker vertically by `sin(clock)` scaled to a 50-reference-pixel amplitude (so the highest point is 50px above its placed position and the lowest is 50px below, exactly as specified) — expressed in the same reference-space pixels as every other distance in this app's data model (`entity.x`/`y`, `BOUNCE_AMPLITUDE`, etc.) and multiplied by the render's own `scale` factor at the point of use, so the bounce looks the same size on the windowed stage, in a full-world zoomed-out view, and in an export at a different resolution — not a fixed number of *canvas* pixels, which would look larger on a 1920x1080 export than on the 1280x720 stage. Sway reuses the character sway's exact look (7°, a 0.75s cycle) but drives the angle from the sticker's own `visibleClock` instead of an actual walk phase, since a sticker sways continuously once visible regardless of whether it's moving. Spin is a plain linearly-increasing angle, completing a full 360° every 2 seconds (a judgment call — the brief specified the 360° rotation but not a rate). All three reuse the same rotate-about-bottom-center / translate-by-offset drawing approach a character's own sway/bounce already uses, just applied directly to the sticker's `ctx.save()/translate()/rotate()/restore()` rather than needing a dedicated draw function.

Verified with a deterministic unit-style test rather than real-time screenshots (real-time waits would make exact milestone angles like a quarter-turn flaky to hit): drove `SceneRuntime.render()` directly with hand-picked `dt` values so the sticker's clock lands exactly on quarter/half/three-quarter-cycle milestones, then read canvas pixel data back out to confirm bounce moves the sticker's topmost visible content up then down by exactly the expected scaled amplitude, sway's content shifts horizontally and reverses direction between the quarter and three-quarter points, spin vacates the sticker's original center column at a 90° turn, static stays pixel-identical across frames with varying `dt`, and toggling a sticker off mid-bounce-peak immediately redraws it (faintly) at its neutral row rather than at the peak. This same pass also caught the reference-space-vs-canvas-pixel scaling bug above — an earlier version applied the 50px bounce amplitude directly in canvas pixels, which the deterministic test's exact-pixel-offset assertions didn't match once accounting for the stage's 0.5x scale factor.

## Gamepad + keyboard

`src/engine/input.js` polls `navigator.getGamepads()` every animation frame and always also reads keyboard state, so every gamepad action has a keyboard equivalent — both because a keyboard is a reasonable fallback, and because a physical gamepad can't be exercised in an automated test.

Every key this app reads (arrows, WASD, Space) is also a key the browser scrolls the page with by default, so `InputSource` calls `preventDefault()` on those specific key events — otherwise puppeteering with the keyboard fallback scrolls the stage out of view.

Mapping: left stick / d-pad → move (Arrow keys / WASD), face button 0 or right trigger → hold to talk (Space), left/right bumper → step to the previous/next pose (`[` / `]`). Eye direction and blinking remain fully automatic with no input mapping at all.

Pose-stepping is edge-triggered (one step per press), unlike movement/talk which are level-based (read as "currently held" every frame). Keyboard presses are trivial to edge-detect (the `keydown` handler itself only fires once per physical press, ignoring OS auto-repeat via `e.repeat`), but the Gamepad API has no press events at all — every button is polled as a snapshot each frame — so the bumpers need their own from-scratch edge detection: `InputSource` remembers last frame's polled `pressed` state for buttons 4/5 and only counts a step on the false→true transition.

## Dialogue audio

A scene can have exactly one imported dialogue audio file (`scene.dialogueAudio = {assetId, duration}`), meant for a track recorded/mixed externally with all characters' lines already laid out on one timeline. It's stored as an ordinary asset blob, decoded once with the Web Audio API to draw a waveform (`src/engine/audio.js`) in the Animate view's Timeline panel, and its duration becomes a floor for the overall scene length (`sceneDuration()`) so "Play all" and export run for at least as long as the dialogue.

Playback sync is a plain `<audio>` element whose `currentTime` is set to match the scene clock whenever recording/preview starts (and paused/resumed alongside it) — there's no drift correction beyond that, which is fine for the short clips this is meant for. The animator is expected to listen to it while puppeteering and hold the talk button at the right moments (the existing mouth/speech-bubble mechanism), rather than the app trying to auto-detect who's speaking when from a single mixed-down track.

For export, the dialogue audio is decoded again into an `AudioBufferSourceNode`, routed through a `MediaStreamAudioDestinationNode`, and its audio track is combined with the canvas's `captureStream()` video track into one `MediaStream` before handing it to `MediaRecorder` — so the exported file has a real muxed audio track (verified with `ffprobe`/`volumedetect`), not just video.

## Export

Canvas capture via `canvas.captureStream()` + `MediaRecorder`, recording webm (with an opus audio track mixed in when the scene has dialogue audio). The export view plays the full composited scene at real time speed while capturing, then offers the result as a download. Resolution/frame rate default to 1280x720 @ 30fps; a control for picking an alternate resolution/frame rate is exposed since it was cheap to add.

Changing resolution/fps constructs a fresh `SceneRuntime` at export time (its canvas is a different size than the editor's), and that runtime's `preload()` must be awaited before rendering starts — `preload()` is what populates the shadow image, speech bubble frames, and shadow-width caches (`this.fx`, `shadowWidthFractionBy*IdMap`) on that specific instance; a `SceneRuntime` with those left at constructor defaults still renders characters and objects fine (their images come from the separate module-level image cache) but silently draws no shadows or bubbles. This was missed on the export view's "Render video" button specifically (the initial static preview on that page did call `preload()`), which is why exported video was missing shadows/speech bubbles while the live editor and puppeteering views, which already awaited it, looked correct.

Neither the camera nor multi-pose characters needed any changes to `export.js` at all — both are handled entirely inside `SceneRuntime.render()`/`sampleTrackAt()`, which export.js already calls the same way it always has. That both features "just worked" in an exported video on the first try (verified below) is a decent sign the position/pose-stream-driven architecture is paying for itself.

## Known simplifications (given the "work independently" brief)

- The "move cycle" and "talk loop" are just an ordered list of frames the user assigns and are stepped through by elapsed time — there's no concept of matching cycle speed to actual movement speed beyond capping the walk-phase oscillation rate at top speed. Fine for the flat crayon-style sample art; a more physically-accurate walk cycle would need pose data this art doesn't have.
- Scrubbing a recorded track backward during playback can cause a visible flip-turn glitch (the flip state machine assumes forward time). Play/pause/restart all work correctly; only manual backward scrubbing is affected, and it self-corrects within one flip cycle.
- Object props are static per scene (position/scale/z only, no animation) since the spec explicitly describes them as non-posed.
- Dialogue audio is one file per scene with no in-app trimming/offsetting — it always starts at scene time 0. It's meant to be fully assembled in external audio software first, per the given direction, so this wasn't built out further (no per-clip placement/multi-track).
- Audio/video sync during live preview is "set `currentTime` once and let both clocks run," not frame-accurate drift correction — acceptable for short dialogue clips, but a very long recording session could drift a little between the visual scene clock and the audio element's own playback clock.
- Camera follow supports both axes but still only one designated character per scene — matching what was actually asked for. Multiple independently-moving characters in a large scene would need a group-framing policy (follow a centroid, zoom to fit) this doesn't attempt.
- Folders are flat (no nesting) and an asset can be in at most one — enough for "a folder for backgrounds," not a general filing system.
- Solid objects only block characters, not each other, and only via the recorder's step-by-step integration during live recording — dragging an object or character to overlap a solid one in the editor isn't prevented (placement is unconstrained everywhere else in this app too).
- A sticker's appear/disappear state is a live-performance input, recorded the same way its position is — there's no declarative "appear at exactly t=2.3s" timeline edit, no scrubbable keyframe for visibility, and re-recording a sticker always starts it hidden again rather than continuing from wherever a previous take left it. Good enough for "press a button to make something pop in," not a general-purpose timeline editor.
- A sticker's spin rate (360° every 2 seconds) and the sway/bounce cycle length (0.75s, borrowed from the character sway cycle) are judgment calls — the brief specified spin's full rotation and bounce's exact ±50px amplitude but not a rate for either motion.
- Punch-in has no separate "punch-out" marker — Stop is the only out point, and everything the old track had after wherever the new take happens to end is discarded, not kept. Re-fixing a short stretch in the *middle* of a longer take means the new take has to run back out past wherever the original would otherwise have continued, or that tail is simply gone.
- The scene editor's pose-sequence control is append-from-palette + remove-by-position, not free drag-reordering — covers building an ordered, repeatable loop like `idle, handsUp, idle, running, idle` with much less UI; fixing a wrong order means removing and re-adding in the right order rather than dragging an item into place.
